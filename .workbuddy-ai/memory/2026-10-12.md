### 關鍵研究結論
- `~/.grok/auth.json` 是 **map 結構**，key 為 scope 字串 `https://auth.x.ai::<client_id>`，
  value 含 `key`(access token JWT) / `refresh_token` / `email` / `user_id` / `expires_at` /
  `oidc_client_id` / `oidc_issuer`。Grok CLI 會 **hot-reload** 此檔，換檔即換帳號、免重啟。
- OAuth client_id: `b1a00492-073a-47ea-816f-4c329264a828`；issuer `https://auth.x.ai`。
- **額度查詢端點**：`GET https://cli-chat-proxy.grok.com/v1/billing?format=credits`（週）
  與 `GET .../v1/billing`（月）。
  Headers: `Authorization: Bearer <token>`、`Accept: application/json`、
  `x-grok-client-mode: cli`。
- **重要**：`auth.json` 裡的 token 常常已過期，直接打會回 **401**
  `Invalid or expired credentials (... upstream=PermissionDenied)`。
  必須先 refresh：`POST https://auth.x.ai/oauth2/token`
  with `grant_type=refresh_token&refresh_token=<rt>&client_id=<cid>`，
  再帶新 token 重打 → 200。
- 週報表欄位：`config.creditUsagePercent`（**方案無上限時此欄位不存在**）、
  `config.currentPeriod.{type,start,end}`、`config.productUsage[].{product,usagePercent}`、
  `onDemandCap/onDemandUsed/prepaidBalance`（皆為 `{val:n}` 包裝）、`isUnifiedBillingUser`。
- 月報表欄位不同：`config.{monthlyLimit,used,history[]}` → 需自行用 used/limit 推算百分比。

### 第八輪：install.cmd 無限亂碼迴圈 → CRLF 兩段式真因（重點）
使用者截圖顯示跑 `install.cmd` 時出現 **無限亂碼迴圈**（cmd.exe 反覆吐出片段文字）。

**真因（第一層）**：`install.cmd` 是 **LF-only** 結尾。Windows CMD 需要 **CRLF**，
bare LF 會讓 `for /f`、括號區塊被錯誤解析 → 亂碼迴圈。
修法：轉成 CRLF + 加 `.gitattributes`。

**真因（第二層，關鍵教訓 — 第一次修完其實還沒生效）**：
原本寫的 `.gitattributes` 是 `*.cmd text eol=crlf`。這代表 git **在 object 裡存的是 LF**，
只在 checkout 到工作區時才展開成 CRLF（`git ls-files --eol` 顯示 `i/lf w/crlf`）。
**但 GitHub raw 端點是直接吐 blob**，所以 `curl -fsSL .../install.cmd` 下載到的仍是 **LF**，
福使用者端照樣壞掉。

正確修法：把規則改成 **`*.cmd -text`**（`-text` = 不做任何 EOL 轉換，verbatim 存進 blob）。
改完 `git add --renormalize` 後 `git ls-files --eol` 變成 `i/crlf w/crlf`，
blob 內真的是 148 CRLF / 0 bare LF，raw 端點才吐得出正確檔。

**真因（第三層）：CDN 快取延遲**
即使 blob 已是 CRLF，剛 push 完 `raw.githubusercontent.com/<branch>/install.cmd`
仍可能回舊的 LF 版本（branch 名走 CDN，TTL 長）。
→ 因此兩個 installer 都改成 **先用 GitHub API 把 branch 解析成 commit SHA，
再 `git fetch --depth 1 <sha>`**（SHA 不可變、永不過期）。
取不到 API 時才 fallback 回 branch 名。更新路徑（已安裝後再跑）也套用同一邏輯。

**驗證**：
- `git ls-files --eol install.cmd` → `i/crlf w/crlf attr/-text`
- commit-pinned raw URL → CRLF 正確
- branch raw URL（等 CDN 追上後）→ 178 CRLF / 0 bare LF
- 實跑文件上的原始 one-liner → 完整跑完、exit 0、"Installation complete"
- 安裝副本 git log 在 tip commit、`bin/gs.js where` 正常
- `npm test` → 21/21

**附帶修正**：`install.cmd` 內兩個 em-dash（UTF-8 `e2 80 94`）在預設 OEM 主控台
（cp437/850）顯示成 `??`。已全部換成 ASCII `-`，現在整檔純 ASCII。

**教訓**：
1. Windows `.cmd`/`.bat` 要 CRLF，但**別用 `text eol=crlf`** — 要用 `-text` 才能在 blob 裡保住 CRLF。
2. 一鍵安裝腳本若靠 raw URL 取檔，**要考慮 CDN 快取**：改用 commit SHA 最穩。
3. 改完要驗「使用者真正會下載到的那個 URL」，不是只驗本地檔案。

## macOS / Linux 一鍵安裝：新增 `install.sh`

**背景**：專案現在在 macOS 上開發（`/Users/feng33/Documents/MultiGrokState`），
原本只有 Windows 的 `install.ps1` / `install.cmd`。新增 POSIX sh 版。

**一鍵指令**
```
curl -fsSL https://raw.githubusercontent.com/goldshoot0720/MultiGrokState/main/install.sh | bash
```
選項要接在 `bash -s --` 後面；也支援同名環境變數
（`INSTALL_DIR` / `REPO` / `BRANCH` / `NO_LINK=1` / `FORCE=1`）。

**五個非顯而易見的設計點（都是踩過的坑，勿簡化掉）**

1. **stdin 重執行**：`curl | bash` 是把腳本從 **stdin** 餵給 shell，shell 邊讀邊執行。
   第一個讀 stdin 的子程序（`npm`、`git`、Xcode CLT 提示）會把剩下的腳本吃掉。
   解法：開頭偵測 `[ ! -t 0 ]` 且 `MG_REEXEC` 未設 → `cat` 到 `mktemp` 暫存檔 →
   `exec /bin/sh "$_self" "$@" < /dev/null`。**`< /dev/null` 不能省**，
   否則子行程 stdin 還是 pipe；所以判準要加 `MG_REEXEC` 防無限迴圈。
2. **`npm link` 會 chmod bin 成 0755** → `git status` 報 mode change → 工作區變 dirty →
   `MultiGrokState update` 直接拒絕執行。修法：安裝後
   `git -C "$INSTALL_DIR" config core.fileMode false`（只影響這個 checkout）。
3. **`npm install` 會重寫 `package-lock.json`**（當它跟 package.json 不同步時），
   同樣讓工作區變 dirty。修法：優先用 **`npm ci`**（不寫 lock），失敗才退回 `npm install`，
   最後再 `git checkout -- package-lock.json` 還原。
4. **`npm link` 失敗（EACCES）要能降級**：系統級 Node（nodejs.org pkg / Intel Homebrew）
   的 global prefix 是 root 所有。降級成 `~/.local/bin` symlink，並印出要加的 PATH 行
   （依 `$SHELL` 選 `~/.zshrc` / `~/.bash_profile`）。
5. **`rm -rf` 護欄**：`guard_removal()` 拒刪 `/`、`$HOME`、`$GROK_HOME_DIR`、
   `/usr`、`/etc`、`/var`、`/System`…，以及任何「是 `$HOME` 祖先」的路徑；
   非我們自己的目錄（package.json 不含 `"multi-grok-state"`）除非 `--force` 否則拒絕刪。
   **⚠️ `FORCE` 只能是「使用者明確要求的」**——曾經在「既有安裝不是 git checkout」的分支裡
   偷設 `FORCE=1`，結果連帶授權刪掉外來目錄。已改成另用 `_needs_fetch` 表達。

**順手修掉的真 bug**
- `package-lock.json` **過期**：bin 還記著舊的 `grok-state` / `gs`，
  跟 `package.json` 的 `MultiGrokState` / `multigrokstate` 不一致 → 每次 `npm install` 都弄髒工作區。
  已 `npm install --package-lock-only` 重生。
- `bin/gs.js` 補上 exec bit（`chmod +x`），commit 時記得保留 100755。

**測試方式**：`cat install.sh | sh -s -- --install-dir /tmp/xxx --no-link`

## 真因：bin 名稱只差大小寫 → `npm link` 在 macOS 永遠失敗

使用者跑完一鍵安裝後，我檢查他的機器發現 **`npm link` 其實「有成功又回報失敗」**：
`~/.npm-global/bin/MultiGrokState` 和 `~/.local/bin/multigrokstate` 兩個 symlink 都在。

**線索在 `~/.npm/_logs/`**（npm 的 debug log 是查這類問題的金礦）：
```
error EEXIST: file already exists, symlink
  '../lib/node_modules/multi-grok-state/bin/gs.js'
  -> '/Users/feng33/.npm-global/bin/multigrokstate'
```
`package.json` 同時宣告 `"MultiGrokState"` 與 `"multigrokstate"`，
**APFS 不區分大小寫 → 同一個檔** → npm 建完第一個、第二個撞 EEXIST 而中止。

**修法**
1. `package.json` 只留 `"MultiGrokState"`（全部文件／help／Windows 腳本都只用這個名字，
   小寫那個沒人引用）。`package-lock.json` 同步重生。
2. `install.sh` 不再相信 `npm link` 的 exit code：
   失敗時檢查 `$(npm prefix -g)/bin/MultiGrokState` 是否可執行，
   可執行就報 `_linked=2`（成功）而不是白白降級。
3. 降級分支不再建第二個只差大小寫的 symlink。

**A/B 驗證**（用 `npm_config_prefix=/tmp/...` 隔離，不動使用者的 prefix）
- 舊 package.json：`npm link` → exit 1、`EEXIST`、只生出小寫 symlink。
- 新 package.json：`npm link` → exit 0、`MultiGrokState` 就位、`MultiGrokState where` 正常。
- 另外用「上游還是壞的 package.json」跑 install.sh，確認 `_linked=2` 分支會正確報成功。

**收尾**：使用者機器 `~/.multigrokstate` 已用 `MultiGrokState update` 升到 `a28928b`，
npm link 這次乾淨成功。84/84 測試通過。

**踩到的小坑**：`MultiGrokState update` 在 push 後「立刻」跑會回
「Already up to date」—— GitHub 的 `/commits/{ref}` API 有幾秒的快取。
等一下再跑就正常了，不是程式 bug。

### 補：測試不具隔離性 → 安裝副本永遠 83/84（`e90c7b8`）

修完 bin 名稱後在**安裝副本**（`~/.multigrokstate`，detached）跑 `npm test`，
得到 **83/84**，唯一失敗的是：

```
✖ localStatus marks a real branch as not detached
    {"sha":"4ccd1b0…","branch":null,"detached":true}
```

**真因**：這條斷言測的是**當下 checkout**（`ROOT`）的分支狀態。
`install.sh` 刻意把安裝副本留在 `FETCH_HEAD` 的 detached 狀態
（`src/version.js` 有註解、updater 也依賴這點），所以：

| 跑測試的位置 | 結果 |
| --- | --- |
| 開發 clone（在 `main` 分支）| 84/84 |
| 安裝副本（detached）| 83/84 |

→ **測試 harness 宣稱隔離，卻有一條斷言洩漏了環境狀態。**
開發者在自己機器上永遠看不到，只有真正安裝的使用者會踩到。

**修法**：兩種狀態都在 sandbox 裡用獨立 repo 驗。
- 新增 `branch-probe`：`git init` → `symbolic-ref HEAD refs/heads/main`
  → `-c user.email/user.name` 建一個 empty commit → 驗 `detached === false`、
  `branch === 'main'`、SHA 是 40 碼。
- 原本的 `detached-probe` 改成**離線**：本地 commit 後 `checkout --detach HEAD`，
  不再 `git fetch` 上游的 `local.sha`。整個第 12 節從此不依賴網路與當下 checkout。
- 抽出共用的 `gitIn(dir)` helper，兩邊都用。

**驗證**：開發 clone 86/86、安裝副本（detached）86/86、離線模擬 detached 副本 86/86。
已 push `a28928b..e90c7b8`，安裝副本同步到 `e90c7b8`。

**通則：測試不可以斷言「當下 checkout」的狀態。** 這個工具會被安裝成 detached
checkout，任何讀 ambient git state 的斷言都要改成在暫存 repo 裡造出該狀態。

## 自動 commit/push 慣例（22:35）

使用者要求「以後每次改完自動 commit/push」。做法：

1. **`.git/hooks/post-commit`**（本機、不進 repo）：commit 後自動 push 當前分支到 upstream。
   失敗只印訊息、不擋 commit；`GIT_AUTO_PUSH=0` 可跳過單次。
   detached HEAD / 無 upstream 時靜默跳過。
2. **專案 MEMORY.md** 新增「提交慣例」段（每次改完主動 commit+push）。
3. **user-level MEMORY.md** 新建（原本不存在），記為跨專案工作偏好。
4. 注意：hook 是 per-clone 的，macOS checkout 與安裝副本不會自動有，要另外裝。

下次的 memory commit 剛好當 hook 的端到端驗證。

**踩到的坑**：這個 clone 的 `main` **沒有設定 upstream**（`branch.main.merge` 不存在），
`@{upstream}` 解析失敗 → hook 第一版靜默跳過、根本沒 push。
已修：hook 在沒有 upstream 時 fallback 到 `origin/<branch>`；並補做 `git push -u origin main`。
教訓：**hook 的「靜默跳過」要能分辨「本來就該跳過」與「設定缺失」**，
驗證一定要看遠端 tip 有沒有動，不能只看 commit 成功。
